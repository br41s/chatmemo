# ChatMemo — full application audit

Date: 2026-08-18 · Branch: `claude/chatmemo-app-audit-i091jn` · Commit at audit: `ed72593`

Scope: architecture, UX, visual design, and refactoring. Security was audited
separately on 2026-07-26 and reviewed on 2026-07-29 — it is **out of scope here**
and no security regressions were introduced by these findings.

## Executive summary

ChatMemo is a well-engineered memory system bolted onto an unmodified 2024
fork of Chatbot UI. The memory layer itself is the strongest code in the
repository — documented, unit-tested, defensively coded. Everything the user
actually touches is still the fork.

Three themes account for most of the findings:

1. **The product has no identity.** Every user-facing surface still says
   "Chatbot UI", and the largest element on the empty chat screen is a logo
   linking to a competitor's website.
2. **The memory system is invisible in the product.** The feature the whole
   app exists for has no presence in the chat surface at all.
3. **Two context budgets contradict each other.** The client trims history to
   4096 tokens; the server then prepends up to ~25k tokens of memory. Neither
   knows about the other.

## A. Identity & product surface

### ID-01 — Critical — The app is branded as another product

`app/[locale]/layout.tsx:15-18` sets `APP_NAME`, title, OpenGraph and Twitter
card to "Chatbot UI", with the description `"Chabot UI PWA!"` (typo included).
This is what every browser tab, every shared link preview, and the installed
PWA display. `public/manifest.json:2-3` repeats it.

Worse, `components/ui/brand.tsx:14` wraps the hero logo in
`href="https://www.chatbotui.com"` — the most prominent element on the login
screen and the empty chat screen navigates the user off to a third-party
product. `app/[locale]/page.tsx:17` and `app/[locale]/setup/page.tsx:166`
("Welcome to Chatbot UI") do the same, and `components/chat/chat-help.tsx:47`
links help to `mckaywrigley/chatbot-ui` rather than this repo.

The README brands the product as ChatMemo with a clear value proposition. None
of it reaches the screen. This is the highest impact / lowest effort fix in the
audit.

### ID-02 — High — Memory has no presence in the chat surface

The product thesis is persistent cross-provider memory. In the chat UI there is
no indicator that memory was injected, no view of what was injected, no way to
suppress it for one turn, and no attribution when the model answers from
memory. The "Chat Info" tooltip
(`components/chat/chat-secondary-buttons.tsx:25-40`) lists model, prompt,
temperature, context length, profile context and workspace instructions — and
says nothing about memory.

Memory History and Timeline exist only as unlabeled icons at the bottom of the
far-left rail (`components/sidebar/sidebar-switcher.tsx:88-96`), below eight
inherited Chatbot UI tabs.

### ID-03 — Medium — Empty state teaches nothing

`app/[locale]/[workspaceid]/chat/page.tsx` renders a logo and an input. No
onboarding, no memory stats ("847 conversations remembered"), no suggested
recall prompts. A new user has no way to discover that recall or full-transcript
recovery exist, or which phrases trigger them — and the trigger phrases are a
hardcoded list (`lib/server/get-full-conversation.ts:22-70`) that the user can
only hit by accident.

## B. Architecture

### ARCH-01 — Critical — Two context budgets that contradict each other

`lib/build-prompt.ts:54-101` trims conversation history client-side to
`chatSettings.contextLength`, which defaults to **4096**
(`app/[locale]/[workspaceid]/layout.tsx:168`). The server then prepends the
memory block to the system message: up to 100k chars of baseline
(`get-latest-summary.ts` — 80k personal + 20k bulk), plus 6k of relevance, or up
to **120k chars** of verbatim transcript on a full-conversation hit
(`get-full-conversation.ts:502`).

So the client carefully budgets ~4k tokens and the server silently adds ~25–30k.
The client-side trimming is therefore meaningless, the user's context-length
setting does not describe what is sent, and any model with a small context
window receives an over-limit request and returns a provider 400 that surfaces
as a generic chat failure. The two systems need to share one budget, with memory
retrieval sized against the selected model's real context window.

### ARCH-02 — High — Lessons are dropped for users with no summary rows

`lib/server/get-latest-summary.ts:98`:

```ts
if (personalData.length === 0 && bulkData.length === 0) return null
```

This returns before `lessons` is used, even though lessons were fetched
successfully in the same `Promise.all`. A user who has a populated
`user_lessons` document but no summary rows — or whose summaries were cleared
via the memory panel's "Clear all" — silently loses the highest-quality memory
layer. The instructions block still tells the model `[LESSONS]` is the strongest
signal and to read it first.

### ARCH-03 — High — Up to ~13 database round trips before the first token

Every chat turn runs three memory layers in parallel from an **edge** function
(`inject-memory.ts:106-110`):

- baseline: 3 `summaries` queries + 1 `user_lessons` query
- relevance: up to 4 `ILIKE` queries (`get-relevant-memory.ts:120`)
- full retrieval: up to 4 `ILIKE` + 1 `chats` query + **one `messages` query per
  matched chat** (`get-full-conversation.ts:660-668`)

Nothing is cached. The baseline blob is recomputed identically on every turn even
though it only changes when a summary is written. A per-user cache keyed on the
newest `summaries.created_at` would remove the majority of this work.

### ARCH-04 — High — `summaries` is one TEXT column doing a schema's job

Source, kind, title, date and import watermarks are all encoded as string
prefixes in `content`: `[source:claude]`, `[source:chatgpt:summary]`,
`[chatmemo:watermark:source=X ts=N]`, `### [YYYY-MM-DD] Title`,
`Conversation Index`.

At least five consumers re-parse those prefixes independently, and they have
already diverged:

| File | Watermark predicate |
| --- | --- |
| `get-latest-summary.ts:66` | `.not("content","like","[chatmemo:%]%")` |
| `get-relevant-memory.ts:126` | `.not("content","like","[chatmemo:%")` |
| `get-full-conversation.ts:555` | `.not("content","like","[chatmemo:%")` |

Plus `db/summaries.ts:24` (regex), `app/api/export/summaries/route.ts:33-48`
(`startsWith` chain). Adding typed columns — `source`, `kind`, `title`,
`occurred_at` — would delete most of this parsing, make the filters indexable,
and let the memory UI offer filtering and search.

### ARCH-05 — High — Three unbounded full-table reads

`app/api/summary/history/route.ts`, `app/api/timeline/route.ts` and
`app/api/export/summaries/route.ts` all issue
`select(...).eq("user_id", …).order(...)` with **no `limit`**. The whole point of
the bulk importers is to load thousands of rows of up to 10k chars each, so the
failure mode grows in direct proportion to the feature that sells the product.
`/api/summary/history` additionally ships the entire result to the browser,
where `memory-history-sheet.tsx` renders every row unvirtualized.

### ARCH-06 — High — Workspace load is a serial waterfall that runs twice

`app/[locale]/[workspaceid]/layout.tsx:93-171` performs ten independent queries
strictly in sequence — workspace, assistants, chats, collections, folders, files,
presets, prompts, tools, models — then downloads and base64-encodes every
assistant image, one at a time, all behind a full-page `<Loading />`. Every one
of those queries is independent and could run in a single `Promise.all`.

It also runs **twice on mount**: the `[]` effect at line 62 calls
`fetchWorkspaceData` after the session check, and the `[workspaceId]` effect at
line 74 calls it unconditionally. Because `setAssistantImages` appends
(`prev => [...prev, …]`, lines 112 and 122) rather than replacing, every
assistant image ends up in state twice on first load, and again on each
workspace switch.

### ARCH-07 — High — The model catalog is frozen at May 2024

`types/llms.ts` and `lib/models/llm/*` still list `claude-2.1`,
`claude-instant-1.2`, `gpt-4-vision-preview`, `gpt-4-turbo-preview`,
`gemini-pro-vision`, `gemma-7b-it`, and the entire retired Perplexity `pplx-*`
family. Most of those IDs no longer resolve at their providers. The app works in
practice only because the default model is `openai/gpt-4o-mini` routed through
OpenRouter, whose catalog is fetched dynamically — so the six directly-integrated
providers are largely decorative.

Related crash: `CHAT_SETTING_LIMITS[chatSettings.model].MAX_TOKEN_OUTPUT_LENGTH`
is indexed without a guard in `anthropic/route.ts:77`, `groq/route.ts:36` and
`mistral/route.ts:37`. `CHAT_SETTING_LIMITS` is a `Record<LLMID, …>` covering
only those 36 stale IDs, so any model outside the table throws a TypeError and
returns a 500.

### ARCH-08 — Medium — Summarization re-summarizes the whole chat every turn

`use-chat-handler.tsx:419` fires `/api/memory/summarize` after every turn past
the second. Each call re-reads the last 20 messages and writes a fresh summary
row for the same conversation. A 20-message chat therefore produces ~9 rows
describing the same thing. The only guard is a Jaccard comparison against the
single most recent row for the user
(`app/api/memory/summarize/route.ts:159-170`) — which is the wrong row whenever
two chats are interleaved. This bloats both the table and the injected blob.

### ARCH-09 — Medium — The lessons document can be silently truncated

The lessons pass is a full read-modify-write: read the document, send it to the
model, replace it with the model's output
(`app/api/memory/summarize/route.ts:186-215`) — capped at `max_tokens: 800`. Once
the accumulated document exceeds 800 tokens of output, the model's rewrite is
truncated and `upsertLessons` overwrites the good copy with the truncated one.
There is no length guard, no diff, and no version history for `user_lessons`
(unlike `summaries`, which has both). Two concurrent summarize calls also clobber
each other — last write wins.

### ARCH-10 — Medium — Memory writes are lost on navigation

The summarize call is fire-and-forget `fetch` with no `keepalive: true`
(`use-chat-handler.tsx:419-427`) and its failure handler is an empty catch. If
the user closes the tab or navigates right after the answer finishes — the most
natural moment to leave — the request is cancelled and the turn is never
remembered, with no signal to anyone.

### ARCH-11 — Medium — No server-side data layer and no error boundaries

All reads go through the browser Supabase client from client components, with
RLS as the only guard. That is a defensible choice, but it means nothing renders
until after hydration, and the 116 occurrences of `throw new Error(error.message)`
across `db/*.ts` throw raw Postgres strings into React. There is **no `error.tsx`
and no `not-found.tsx` anywhere in `app/`**, so any one of those becomes the
default Next.js crash screen with no recovery path.

## C. UX

### UX-01 — High — Unusable on mobile

`SIDEBAR_WIDTH = 350` (`components/ui/dashboard.tsx:16`) is a fixed pixel width
applied via inline `minWidth`/`maxWidth`/`width` with no breakpoint and no
overlay/drawer behaviour. On a 375px-wide phone, opening the sidebar leaves ~25px
for the chat. The memory and timeline sheets are likewise fixed at `w-[380px]`.

### UX-02 — Medium — Sidebar rail overflows its own grid

`components/sidebar/sidebar-switcher.tsx:31` declares
`className="grid h-[440px] grid-rows-7"` and then renders **eight**
`SidebarSwitchItem` children (chats, presets, prompts, models, files,
collections, assistants, tools). The eighth lands in an implicit auto row outside
the fixed 440px height.

### UX-03 — Medium — i18n is vestigial and excludes the primary language

`i18nConfig.js` declares 18 locales. `public/locales/` contains two — `en` and
`de` — and `en/translation.json` holds exactly **one** string. Every other label
in the app is hardcoded English. Notably `es` is declared but has no file, while
the memory prompts (`inject-memory.ts`) and the project's own decision log are
bilingual Spanish/English. Either invest in i18n or remove the routing layer;
the current state adds a locale segment to every URL and a middleware pass for
one translated string.

### UX-04 — Medium — Destructive memory actions have no real confirmation

"Clear all" wipes the user's entire memory. It is guarded by a two-click inline
toggle that resets on `onBlur`
(`components/memory/memory-history-sheet.tsx:429-433`) — no dialog, no typed
confirmation, no undo, and no export prompt beforehand, despite a working
backup export sitting in the same panel.

### UX-05 — Medium — Import advertises a limit the platform will not honour

The import routes declare `MAX_FILE_BYTES = 100 * 1024 * 1024`
(`app/api/import/chatgpt/route.ts:23` and siblings) and read the whole upload
with `await fileField.text()` + `JSON.parse` into memory. Vercel caps serverless
request bodies at ~4.5 MB, so a real ChatGPT export is rejected by the platform
before the route runs, and the user sees a raw status code through
`memory-history-sheet.tsx:215`. The UI should state the real limit and the
route should stream-parse, or imports should move to a direct-to-storage upload.

### UX-06 — Medium — Memory panel has no search, filter, or pagination

The Timeline sheet has source/date/search filters. The Memory History sheet —
the panel that actually manages the data — lists every row newest-first with a
120-char preview and nothing else. Finding one entry among thousands of imported
rows means scrolling.

### UX-07 — Medium — Accessibility is effectively absent

A grep for `role=` / `aria-*` across `components/` outside `components/ui/`
returns exactly one hit, on a decorative SVG. Consequences: the streaming
assistant response has no `aria-live`, so screen readers never announce it;
sources toggles, file-item rows and message images are click-only `<div>`s with
no `tabIndex`, no keyboard handler and no role; there is no skip link and no
focus management when sheets open.

### UX-08 — Medium — Chat load fetches everything

`components/chat/chat-ui.tsx:75-146` loads all messages for a chat with no
pagination, then for each message issues a separate `getMessageFileItemsByMessageId`
call (N+1), and downloads every image in the conversation as a blob and converts
it to base64 before the chat renders.

## D. Visual design

### DES-01 — Medium — The palette is stock shadcn, untouched

`app/[locale]/globals.css` is the unmodified shadcn neutral scale —
`--primary` is `0 0% 9%` in light and `0 0% 98%` in dark. There is no brand hue
anywhere in the token set, which is why the product reads as a template. A
single accent hue plus a considered neutral bias would do most of the work of
making it feel like a product.

### DES-02 — Low — Status colors bypass the token system

`text-green-600`, `bg-red-500/10`, `bg-blue-500`, `text-red-500` appear
throughout `memory-history-sheet.tsx`, `timeline-sheet.tsx` and
`app/[locale]/page.tsx`. Semantic colors (success / warning / danger) belong in
the theme so both themes stay consistent.

### DES-03 — Low — Chat width is a duplicated magic-number chain

`sm:w-[600px] md:w-[700px] lg:w-[700px] xl:w-[800px]` is repeated verbatim in
`chat-ui.tsx:196` and `chat/page.tsx:44`. One layout constant or container class.

### DES-04 — Low — Loading states are unstyled text

Workspace and chat load show a full-page spinner; the memory panel shows the
string `Loading…`. Skeletons matching the eventual layout would remove the
perceived stall that ARCH-06 causes.

## E. Refactoring

### REF-01 — 9 chat routes, ~450 lines of near-identical boilerplate

Each of `openai`, `anthropic`, `azure`, `google`, `groq`, `mistral`,
`openrouter`, `perplexity`, `custom` repeats: parse body → `getServerProfile` →
`checkApiKey` → `injectMemory*` → construct SDK client → stream → map errors to
the same two "API Key not found / incorrect" strings. Seven of the nine are
byte-for-byte identical apart from the key field, base URL and provider name.

A `createChatRoute({ provider, keyField, baseURL, buildRequest })` factory plus
per-provider adapters for the two genuinely different shapes (Anthropic content
blocks, Google `parts`) would collapse this to roughly a fifth of its size and
give the memory injector and error mapping exactly one place to live.

Two concrete defects that the duplication is hiding:
- `app/api/chat/groq/route.ts:19` — `checkApiKey(profile.groq_api_key, "G")`;
  the key name is `"G"`, so the raw thrown error reads "G API Key not found".
- `app/api/chat/google/route.ts:41-53` hand-rolls its own `ReadableStream`
  instead of using `textStreamResponse` from `lib/server/streaming.ts`, and
  omits `charset=utf-8` from the content type that every other route sets.

### REF-02 — `get-full-conversation.ts` is 724 lines, half of it hardcoded data

Roughly 350 lines are literal arrays: 40 trigger phrases, 4 trigger regexes, 24
month names, and a ~200-entry bilingual stopword set. Intent detection, date
parsing, topic extraction, ranking and retrieval all live in one module. Split
the data into a `lib/server/memory-terms/` module and the phases into
`detect-intent`, `extract-terms`, `search`, `rank` — each already has clean
seams and three of the four are already exported purely for testing.

The deeper fix is that phrase-list matching and `ILIKE '%term%'` are standing in
for search. Postgres FTS or pgvector over `summaries` (pgvector is already
enabled for `file_items`) would replace both the trigger list and the ranking
heuristic.

### REF-03 — One context with ~60 values and no memoization

`components/utility/global-state.tsx` holds every piece of app state in a single
unmemoized provider — its own first line is `// TODO: Separate into multiple
contexts`. The cost is already visible: `chat-input.tsx:34` carries a local
mirror of `userInput` with the comment *"avoids re-rendering 53+ context
consumers on every keystroke"*. The same problem remains unfixed for streaming —
`chatMessages` lives in the same context and `components/messages/message.tsx`
consumes 14 values without `memo`, so every token re-renders every message,
every sidebar row and the whole switcher.

Split into `ProfileContext`, `WorkspaceItemsContext`, `ChatContext`,
`ChatInputContext` and `ToolsContext`, and memoize each provider value.

### REF-04 — Oversized components

`components/utility/profile-settings.tsx` (763 lines),
`components/memory/memory-history-sheet.tsx` (748 lines, **20 `useState`
hooks** covering four unrelated concerns: history list, import, per-source
clear, backup/restore), `components/timeline/timeline-sheet.tsx` (641),
`components/sidebar/items/all/sidebar-update-item.tsx` (679). The memory sheet
is the priority: four sub-components, and `useReducer` for the import/backup
state machines.

### REF-05 — 1.22 MB First Load JS on the chat route

Against a 90 kB shared baseline. Two static imports account for most of it:

- `lib/build-prompt.ts:3` imports `gpt-tokenizer` (44 MB installed) and runs in
  the browser on every send. Move token counting server-side, or switch to a
  cheap char-based estimate client-side.
- `components/messages/message-codeblock.tsx:5` imports the full
  `Prism` build of `react-syntax-highlighter` (8.9 MB installed), which bundles
  ~300 language grammars. Switch to `prism-light` with registered languages, or
  `next/dynamic`.

### REF-06 — Redundant indexes on `summaries`

Three indexes cover the same access path:
`idx_summaries_user_id (user_id)` and
`idx_summaries_user_id_created_at (user_id, created_at DESC)` from
`20260517000000_add_summaries.sql`, plus `idx_summaries_user_created
(user_id, created_at DESC)` from `20260520000000_perf_indexes.sql` — an exact
duplicate of the second. Two can be dropped; the composite covers the first as a
leftmost prefix.

### REF-07 — Stale comments and dead code

- `20260517000000_add_summaries.sql:26` says *"no updated_at: append-only, rows
  are never mutated"* and *"no UPDATE or DELETE policies"*; a DELETE policy was
  added the next day and the UI now offers delete, clear-all and restore.
  `CLAUDE.md` repeats the "append-only" claim.
- `lib/export-old-data.ts` + `profile-settings.tsx:737` ("Download Chatbot UI
  1.0 data as JSON. Import coming soon!") — migration path from a product this
  user never ran.
- `components/utility/announcements.tsx` — inherited announcement system with no
  content source.
- Commented-out blocks left in place: `use-chat-handler.tsx:159-176`,
  `sidebar-switcher.tsx:82-85`, `advanced-settings.tsx:16-21`.

### REF-08 — Known React correctness issues

- `chat-helpers/index.ts:148` — `createTempMessages` mutates
  `chatMessages[i].message.content` in place before calling `setChatMessages`.
  The decision log already documents one bug caused by this; the mutation is
  still there.
- `chat-helpers/index.ts:471-489` — image `paths` are collected from
  `newMessageImages.filter(obj => obj.file !== null)` but then re-zipped against
  the **unfiltered** `newMessageImages` by index, so paths attach to the wrong
  images whenever any entry has a null file.

## F. Verification & tooling

### TOOL-01 — Critical — The documented verification gate is red on a clean clone

`npm run type-check` fails immediately after `git clone && npm ci`:

```
components/models/model-icon.tsx(2,21): error TS2307: Cannot find module '@/public/providers/mistral.png'
components/models/model-icon.tsx(3,18): error TS2307: Cannot find module '@/public/providers/groq.png'
components/models/model-icon.tsx(4,24): error TS2307: Cannot find module '@/public/providers/perplexity.png'
```

The PNGs exist. What is missing is `next-env.d.ts`, which declares the image
module types — it is in `tsconfig.json:26`'s `include` but gitignored
(`.gitignore:37`) and only regenerated by `next dev` / `next build`.

This matters because `.husky/pre-push` runs exactly `npm run type-check && npx
jest`, so the only CI this project has fails for any contributor who has not
already run a build, and the natural workaround is `--no-verify`.

Fix: commit a checked-in `types/next-env.d.ts` with the two Next.js reference
directives, or add a `pretype-check` step. It is a two-line change that restores
the gate.

### TOOL-02 — High — Vercel does not type-check or lint either

`next.config.js:31-32` sets `typescript: { ignoreBuildErrors: true }` and
`eslint: { ignoreDuringBuilds: true }`. The comment correctly explains why
(the `@huggingface/transformers` type surface OOM-kills the build VM) and
delegates the check to the pre-push hook. Combined with TOOL-01, both ends of
the safety net have holes at once: the local gate fails open, and the deploy
gate does not check. Fixing TOOL-01 closes this.

### TOOL-03 — Medium — Pre-commit hook stages everything

`.husky/pre-commit` ends with `git add .`, so every commit sweeps in unrelated
working-tree changes. `CLAUDE.md` documents the `--no-verify` workaround; the
better fix is `lint-staged`, which formats only what is already staged.

### TOOL-04 — Medium — Test coverage is deep but narrow

223 tests across 26 suites, concentrated on memory transforms, ranking,
term-gating, streaming helpers and RLS migrations — genuinely good. But there
are **zero component tests**, one Playwright spec (login only), and no coverage
of the paths most likely to break: the workspace load waterfall (ARCH-06), the
client/server context-budget interaction (ARCH-01), the import routes, or the
summarize/lessons write path (ARCH-09).
